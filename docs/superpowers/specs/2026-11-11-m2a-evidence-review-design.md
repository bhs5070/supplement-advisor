# M2-A 근거 조사 흐름 설계안

상태: 사용자 설계 승인 후 구현 준비. 사용자는 A(조사 흐름 먼저)를 선택했고 이 상세 설계안을 제시한 다음 “가자”로 계획 작성·EGM 검토·TDD 진행을 승인했다. 최초 A 선택만으로 상세 계약 승인을 추정한 것은 아니다. M2 전체의 점수·추천 기능은 후속 단계에 유지한다. 구현 계획의 개별 명세는 리드 제안이며 승인 설계 안에서 검토·명확화한다.

## 목적과 완료 모습

소비자가 URL을 넣고 심화 근거 조사를 선택하면 기존 M1 식별 결과를 기반으로 Supervisor가 필요한 전문 역할을 선택한다. 전문 역할은 공식 자료·논문을 조사하고, 확인 가능한 사실·상반된 근거·빠진 정보를 출처와 함께 설명한다. 실패하거나 한도에 도달하면 조사한 범위와 남은 항목을 저장한다. 정보 부족을 제품 품질 저하나 안전성 보장으로 바꾸지 않는다.

예: 주요 원료는 확인됐지만 함량이 없는 제품은 해당 원료의 근거와 공식 자료를 보여주되, 연구의 투여량을 이 제품 함량으로 채우거나 완제품 효과를 확정하지 않는다. 비회원 개인 적합성은 미평가다.

완료는 실제 URL→M1 식별→선택적 역할/자료 조사→근거 보고서 저장→권한 조회와 화면 표시를 한 번 연결하고, 선택·재조사·실패·복구의 오프라인 분기 및 기존 M1 회귀를 검증하는 것이다. 넓은 사이트 성공률이나 임상적 판단 정확도 보증은 완료 조건이 아니다.

## 접근 방식과 결정 상태

| 접근 | 먼저 확보하는 것 | 비용·한계 | 선택 |
|---|---|---|---|
| 조사 흐름 먼저 | 실제 근거·출처·누락과 Supervisor 실행 | 점수·추천은 후속 구현 | 사용자 A 선택 |
| 평가 기준 먼저 | 점수와 추천 조건의 사전 정의 | 실제 근거 관찰 전 설계 논의 증가 | 이번 순서에서 선택하지 않음 |

기존 Worker·DB·수집 그래프를 유지하고 새로운 조사 그래프와 보고서 계약을 덧붙이는 방식을 리드가 제안한다. 기존 수집 그래프 안에 Supervisor·모든 도구를 한꺼번에 넣지 않는다. M1 독립 실행과 과거 보고서 호환을 검증하기 쉽기 때문이다. 이는 아래 세부 설계와 함께 승인받을 제안이다.

## 포함·제외

- 포함: Supervisor1+고정 전문5역할 정의, 필요한 역할 선택, 도구를 이용하는 제한된 조사 루프, 근거 출처 정리, 한정 재조사, 부분 결과 저장·복구, API/화면 연결, 실제 한정 연동 확인.
- 제외: M2-A 점수 산정·구매 추천, 회원·개인 건강정보·영양소 추천, 이미지/OCR/JS 수집 확장, RAG/벡터DB, 모델 교체, LangSmith/R2 운영 확장, 임상 처방·진단.
- 기존 React/TypeScript/Vite·FastAPI·SQLAlchemy/PostgreSQL·Celery/Redis·HTTPX·LangGraph·GPT-5.6 Luna와 개발 Sol/Luna 구성은 유지한다. 제품 런타임 역할을 생성·복제하거나 역할별 서버를 만들지 않는다.

## 입력과 M1 호환

`POST /api/analyses`에 선택 필드 `mode: collection | evidence_review`를 추가한다. 생략 시 기존 `collection` 동작이다. 새 화면은 URL 입력 시 사용자가 심화 근거 조사 여부를 선택할 수 있게 하며 조용히 추가 비용 경로로 전환하지 않는다.

DB Analysis에 mode를 영속화한다. migration0003의 기존 행 기본값은 collection이다. 기존 token·id·상태·1회 보완 API와 권한404 계약은 보존한다. GET은 mode와 기존 report를 반환하며 과거 클라이언트와 저장 보고서를 유지한다.

M2 요청도 M1을 먼저 실행한다. 기존 missing_fields가 있으면 현재 한 번의 입력 보완 흐름으로 멈춘다. 보완 후에도 필요한 식별정보가 없으면 확인한 M1 보고서를 유지하고 추가 조사 미실행 이유로 종료한다. 보완으로 충분해지면 같은 mode와 남은 예산으로 조사 단계에 진입한다. M2를 위해 추가 입력 횟수를 초기화하거나 새 토큰을 발급하지 않는다.

조사 진입의 충분성은 기존 수집/보완 그래프가 생성한 `missing_fields`가 빈 배열인지로 판단한다. 별도의 공식 matched 강제 조건을 추가하지 않는다. 따라서 미확인 공식 정보는 계속 미확인이며, 전문 역할은 보고서의 실제 식별·출처 수준 안에서만 조사한다. 보완 경로는 기존 저장 보고서와 사용자 입력으로 공식 재대조한 결과를 사용하고 URL 재수집·모델 재추출을 자동 수행하지 않는다.

| 조건 | API 작업 상태 | 보완 가능 | 조사 표시 |
|---|---|---|---|
| M1 정보 부족, 보완 미사용 | needs_input | 기존 can_supplement=true | not_started / identity_information_missing |
| 보완 후에도 M1 정보 부족 | needs_input | can_supplement=false | not_started / identity_information_missing |
| M1 충분, 조사 일부/전체 실행 | completed | false | 조사 결과에 따라 completed/partial/unavailable |
| 안전한 부분 보고서조차 만들 수 없는 처리 실패 | failed | 기존 조건 유지 | 확보한 M1 보고서가 있으면 보존 |

기존 needs_input 오류 코드 `insufficient_information`을 유지한다. 새 조사 단계 사유는 조사 객체에 두며 작업 상태를 새 enum으로 늘리지 않는다. 정보 부족의 불가능한 재입력 버튼을 다시 열지 않는다.

Supervisor의 재조사는 같은 Analysis 안에서 남은 예산·스냅샷·재지시 횟수를 이어간다. 완료/부분 종료된 Analysis를 재개하는 새 사용자 API는 M2-A에 추가하지 않는다. 사용자가 기존 URL 접수 폼에서 명시적으로 다시 제출하면 기존처럼 새 Analysis와 새 토큰이 생기지만 자동 재시도나 같은 작업의 예산 리셋으로 사용하지 않는다. UI가 부분 실패를 이유로 새 요청을 자동 발행하지 않게 검사한다.

공식 후보나 검색 실패를 확정 제품으로 승격하지 않는다. M1에서 주요 원료를 식별한 사실과 원료의 일반 연구 근거를 구분한다. 함량·제형·대상군이 부족하면 적용 가능성은 미확인이다. 등록 일치는 효과·안전성 증명이 아니다.

## 역할 계약

| 역할 ID | 조사 질문 | 허용 근거 | 미평가/보류 조건 |
|---|---|---|---|
| composition | 표시 성분·함량·섭취 기준에 무엇이 확인됐는가 | M1 표시·사용자 보완·공식 표시 자료 | 없는 함량·단위·기준을 추정하지 않음 |
| claims | 표시된 기능·광고를 어떤 근거가 뒷받침하거나 제한하는가 | 공식 기능성 문서, 논문, NIH ODS | 원료 연구를 완제품 효과로 확대하지 않음 |
| personal_fit | 개인 목표·건강정보와 맞는가 | 이후 회원의 동의한 프로필 | M2-A 비회원은 not_applicable, 모델 호출0 |
| safety | 알려진 일반 주의사항과 확인되지 않은 조건은 무엇인가 | 공식 문서, NIH ODS, 논문 | 개인 약물·질환 안전 판정을 하지 않음 |
| official_quality | 등록·표시 대조에서 확인한 범위는 무엇인가 | M1 official_match와 공식 문서 | GMP·등록을 실측 품질 보장으로 바꾸지 않음 |

Supervisor는 입력·M1 근거·누락·남은 예산으로 역할과 조사 질문을 구조화 출력한다. 역할은 enum allowlist만 사용한다. 모든 역할을 무조건 호출하지 않으며, 미호출 역할에도 이유를 남긴다. 이미 충분한 공식 대조는 재조회 대신 기존 출처를 재사용할 수 있다. 각 선택 역할은 허용 도구·검색어·다음 행동/종료를 스스로 선택한다. 정적 요약 함수를 Agent 조사라고 부르지 않는다.

전문 역할은 완료/부분 완료/근거 부족/미평가/외부 기능 미설정/실패를 구분하고, 결과에 질문·확인 사실·해석·빠진 정보·출처 ID·종료 이유를 포함한다. 모델이 없는 출처 ID를 생성하거나 원문에 없는 인용을 붙이면 해당 판단을 채택하지 않는다.

Supervisor는 역할 결과를 검토하고 부족한 질문만 재지시하거나 종료한다. 재지시는 총2회·같은 역할1회이며 실패 재시도와 별도로 기록한다. 서로 모순되는 결과를 합의로 위장하지 않고 보고서에 남긴다.

## 도구와 출처

새 외부 SDK를 추가하기보다 기존 HTTPX와 구조화 OpenAI 호출을 사용한다. 도구는 M1 공식 자료 재사용, 공식 문서 탐색·수집, 문헌 검색·초록 조회로 제한한다. 모든 모델·검색 결과·원문은 명령이 아닌 불신 데이터다.

- Tavily는 공식 도메인/논문 발견용이다. basic, 작은 결과 수, 자동 파라미터·생성 답변·이미지 비활성을 명시한다. 검색 순위와 생성 답변을 근거로 채택하지 않는다. 검색 snippet은 discovery로 구분하고 실제 조회 문서/초록 없이는 substantive 판단의 증거로 쓰지 않는다.
- 문헌 도구는 PubMed/E-utilities와 Europe PMC의 문서화된 엔드포인트를 사용한다. 실제 구현 시 현재 스키마·요청 제한·반환 종류를 공식 문서와 응답으로 확인한다. 서비스 오류를 서로의 성공으로 위장하지 않는다. 두 제공자의 같은 PMID 또는 DOI는 중복 근거로 세지 않는다. 일치 ID가 없으면 무리하게 제목으로 병합하지 않는다.
- NIH ODS·식약처/식품안전나라 공식 문서는 공개 HTML 범위를 안전 수집한다. PDF 전문 판독은 이번 첫 경로에서 필수라고 가정하지 않으며 지원하지 못하면 문서 접근 한계를 표시한다.
- 사용자/모델이 제시한 URL은 기존 SSRF 검증·리디렉션/DNS 재검증·크기/시간 제한을 통과해야 한다. 서비스 고정 API 주소도 allowlist·TLS·응답 크기/형식 제한을 적용하고 임의 URL로 키를 전송하지 않는다.
- 외부 요청 timeout은 기존 최대15초, 모델은 최대30초·SDK 자동 재시도0을 유지한다. 모델 출력/검색·원문 길이를 제한한다. 응답 오류 원문·토큰·키·인증 URL은 기록하지 않는다.

출처는 id, kind, title, 안전한 공개 URL, retrieved_at, provider, document_id/PMID/DOI, 발행/갱신 시점(실제 확인 시), 짧은 인용, 조회 범위(abstract/full document/discovery)를 가진다. 발행일을 수집일로 채우지 않는다. 전문을 읽지 않았으면 읽었다고 하지 않는다. 링크·ID만으로 내용 확인 완료를 주장하지 않는다.

## 보고서와 화면

수집 보고서 `collection_only`는 그대로 둔다. M2-A는 `scope=evidence_review`, `score=null`, `verdict=hold`로 구분한다. 여기서 hold는 아직 구매 판정을 수행하지 않았다는 의미이며 제품 비추천이 아니다.

새 보고서는 M1 기초 보고서, 역할별 조사 결과, 조사 상태(completed/partial/unavailable), 근거 출처, Supervisor 선택·재조사·종료 요약, 빠진 정보와 한계를 포함한다. 원료 근거와 완제품 적용 여부를 별도 필드로 구분한다. 완료된 조사라도 모든 질문에 답했다는 뜻은 아니다.

화면에는 조사 진행 단계, 역할별 상태·미호출 이유, 근거와 반대/제한 근거, 원문 링크·조회 범위·시점, 남은 정보, 미평가 항목을 보여준다. 점수 별·추천 뱃지는 추가하지 않는다. M1 표시와 수동 보완 출처, 토큰 보호를 보존한다. 기존 컴포넌트와 스타일을 재사용하고 UI Skill의 좁은 검색·실제 desktop/mobile 검사로 확인한다.

## 실행 한도·병렬·중단·복구

총20회는 기존 수집/추출/공식 조회와 새 Supervisor·역할 모델·검색·문서 요청을 포함한 실제 외부 요청 시도 단위다. API 내부 여러 문서 fetch는 각각 계수한다. 역할당6회, 동시 전문 역할 최대3을 유지한다. Supervisor 호출도 총20에 포함하며 전용 카운터로 기록한다. 오류 재시도는 일시 오류에만1회, 실제 예약 한도에 포함하고 SDK 재시도는 켜지 않는다.

활성180초·한 시도60초·최대3시도·240초lease와 hard limit은 유지한다. 각 시도는 기존처럼60초 창을 시작 전에 DB 예약하고 중단 시 환급하지 않는다. 병렬 호출 때문에 활성 시간을 개별 요청 timeout의 합으로 중복 차감하지 않는다. 실제 도구 요청은 공통 원자 DB 예약으로 총량을 막고 역할별 로컬 카운터는 동기화한다. 모든 비용 카운터는 재개 시 복원한다.

시도 창이 남지 않아 다음 모델/도구를 시작할 수 없으면 완료된 노드와 부분 보고서를 먼저 저장하고, 현재 claim_token에 조건을 건 graceful yield로 queued에 돌린다. 새 repository 연산은 현재 유효 claim에서만 snapshot·부분 report·queued·lease 해제를 원자 변경한다. 시도 횟수·활성/도구 예약·보완 사용은 초기화하지 않는다. beat가 재발행하며 중복 Worker는 claim/finish fencing으로 차단한다. 이는 승인 대상의 새 제어 연산이며 기존 terminal finish를 몰래 재사용하지 않는다.

3번째 시도나 총 예산 마지막에는 새 작업을 시작하지 않고 마지막 저장 근거로 partial을 종료한다. 총량 부족·시간 부족·외부 실패를 이유별로 기록하고 M1 보고서를 지우지 않는다. 초기 수집/입력 실패는 기존 작업 상태를 따른다. 조사 단계 일부 실패는 안전한 partial 보고서가 있으면 completed 작업/partial 조사로 구분한다.

새 M2 snapshot은 mode·version·입력/기초 보고서 fingerprint·역할 상태·예산/재지시·출처 registry를 가진다. M1 collection snapshot과 별도 키로 보존한다. 호출을 시작하기 전 durable in-flight 표식을 저장하고 완료 결과를 저장한 뒤 표식을 해제한다. crash가 발생한 불명확한 요청을 자동 중복 호출하지 않고 unknown_interrupted로 남기며 사용한 예약은 유지한다. checkpoint 저장 실패/lease 상실 시 후속 호출·완료 저장을 중단한다.

## 보안과 데이터

비회원 토큰과 private/no-store 조회를 유지한다. 브라우저에 API 키·모델 프롬프트 전체·운영 로그를 전달하지 않는다. 역할 지시와 검색 쿼리에 회원 정보는 없고 비공개 원문을 불필요하게 전송하지 않는다. 출처 링크는 http(s)만 렌더링한다. 저장 모델 출력은 길이·enum·source registry로 검증하며 UI에서 HTML로 직접 삽입하지 않는다.

## 구현 경계와 다음 절차

리드: 공통 계약·mode/API/Worker 연결·통합·기록. runtime 작성자: 새 조사 graph/구조화 역할 계약·관련 테스트. evidence 작성자: 외부 도구·출처 정규화·관련 테스트. UI 작성자: frontend만. DB 전용 변경이 필요하면 리드가 순차 소유하거나 별도 슬롯에 배정한다. 같은 시점의 수정 파일은 겹치지 않게 하고 리드 포함 최대4개를 유지한다. 독립 QA 슬롯은 작성 단계가 끝난 뒤 확보한다.

이 문서는 실제 코드 연결점을 읽은 리드 제안이다. 구현 세부 함수·파일의 적절한 분리는 작성자가 정하되 위 계약·역할·보존 조건을 바꾸지 않는다. 사용자가 승인하기 전 제품 코드를 쓰거나 의존성·배포·DB migration을 실행하지 않는다. Superpowers builder check로 중요한 미정 사항을 먼저 찾고, 중요한 runtime/무결성 변경은 EGM 검토 범위를 제시해 독립 검토 후 승인받는다. 승인 뒤 writing-plans에서 구체 파일·테스트·단계별 실행 계획을 만든다.
